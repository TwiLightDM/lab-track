### Обоснование выбора Kanban

- **Состав команды — 2 человека.** Scrum предполагает роли (Product Owner, Scrum Master) и церемонии (планирование,
  дейли, ревью, ретро) — для двоих это избыточные накладные расходы. Kanban не требует ролей и обязательных церемоний;
  синхронизация вт/чт 30 мин закрывает потребность в координации.
- **Поток задач непредсказуем по объёму и приоритету.** Проект «Учёт оборудования лаборатории» — учебный/внутренний,
  требования уточняются по ходу. Kanban не фиксирует scope на итерацию, поэтому не возникает ситуации «итерация сорвана,
  потому что приоритет сменился». Задачи просто двигаются по доске по факту.
- **Разная природа задач.** В бэклоге есть и фичи, и багфиксы, и инфраструктура (CI/CD), и документация. Kanban-доска с
  едиными колонками и WIP-лимитами работает для любого типа задачи; Scrum-итерация с фиксированным набором плохо ложится
  на разнородный поток.
- **Время реакции важнее ритма.** Срочное (блокер/дедлайн) решается звонком и немедленным взятием в работу — в Kanban
  это естественно (освободили слот в WIP — взяли срочное), в Scrum пришлось бы ждать итерации или ломать её.
- **Прозрачность и метрики.** Kanban даёт естественные метрики потока (lead time, throughput, WIP) без дополнительного
  учёта — они же используются для обоснования WIP-лимитов через закон Литтла и для пересмотра соглашения при накоплении
  проблем.
- **Низкий порог входа.** Для команды из 2 человек важно не тратить время на процесс ради процесса: доска + WIP-лимиты +
  договорённости о ревью — минимальный набор, который сразу работает.

### Обоснование WIP-лимитов (закон Литтла)

Закон Литтла: **L = λ × W**, где

- **L** — среднее число задач в системе (в работе / в ревью),
- **λ** — пропускная способность (задач в единицу времени),
- **W** — среднее время прохождения задачи (lead time).

Отсюда **W = L / λ**: при фиксированной пропускной способности время прохождения задачи пропорционально числу
одновременно открытых задач. Ограничивая L, мы ограничиваем W — задачи не «застревают» в очереди.

Для команды из 2 человек:

- **«В работе» ≤ 2** — по одной активной задаче на участника. Дальнейшее увеличение L не повышает λ (люди не могут
  работать параллельно над несколькими задачами эффективно), но увеличивает W — растёт время до завершения каждой задачи
  и множатся переключения контекста.
- **«Ревью» ≤ 2** — ревью делает второй участник, то есть это тот же ресурс, что и «В работе». Суммарный WIP на
  человека ≤ 2: одна задача в работе + одна в ревью. Это держит λ на максимуме, а W — предсказуемым.

Практический эффект: при L = 4 и λ ≈ 1 задача/день W ≈ 4 дня; при L = 2 и той же λ W ≈ 2 дня. Лимиты выбраны так, чтобы
минимизировать W при сохранении λ, и проверяются по факту (если λ падает — лимиты пересматриваются в рамках пересмотра
соглашения).

### Обоснование выбора доски

Используется **GitHub Projects** (доска внутри GitHub-репозитория проекта).

Почему GitHub Projects:
- **Единая среда.** Задачи, код, PR и CI уже в GitHub — отдельный трекер не нужен, не приходится синхронизировать статусы вручную.
- **Связь задачи и PR.** Issue/карточка автоматически связывается с PR и коммитами; при merge в `main` карточка может закрываться/двигаться по правилам проекта.
- **Kanban из коробки.** Поддерживаются колонки, WIP-лимиты и drag-and-drop — ровно то, что зафиксировано в соглашении.
- **Бесплатно и без администрирования.** Для команды из 2 человек не требуется отдельный сервер/подписка; доступ — по правам репозитория.
- **История и прозрачность.** Все переходы видны в истории карточки — это же служит источником метрик потока (lead time, throughput, WIP) для пересмотра соглашения.
