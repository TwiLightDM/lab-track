# Стратегия ветвления (GitHub Flow)

## 1. Общие положения

В проекте используется стратегия ветвления **GitHub Flow**.

GitHub Flow предполагает наличие основной ветки `main`, которая всегда должна содержать стабильную и готовую к
использованию версию проекта. Разработка новых функций, исправление ошибок и другие изменения выполняются в отдельных
ветках.

Все изменения попадают в `main` исключительно через Pull Request (PR) после прохождения проверок и получения одобрения
от другого участника команды.

## 2. Основные ветки

### main

Основная ветка проекта.

Правила:

- Содержит стабильную версию проекта.
- Прямые коммиты запрещены.
- Все изменения принимаются только через Pull Request.
- Перед слиянием PR должен пройти CI.
- Для слияния требуется минимум один Approve от другого участника команды.

### Рабочие ветки

Для выполнения задач создаются отдельные ветки на основе актуальной версии `main`.

Используются следующие типы веток:

| Тип ветки   | Назначение                           | Пример                       |
|-------------|--------------------------------------|------------------------------|
| `feature/`  | Разработка новой функциональности    | `feature/equipment-search`   |
| `fix/`      | Исправление ошибок                   | `fix/equipment-status`       |
| `docs/`     | Изменение документации               | `docs/update-readme`         |
| `refactor/` | Рефакторинг кода                     | `refactor/equipment-service` |
| `test/`     | Добавление и изменение тестов        | `test/equipment-repository`  |
| `chore/`    | Технические и вспомогательные задачи | `chore/update-dependencies`  |

## 3. Правила именования веток

При создании веток необходимо соблюдать следующие правила:

- Использовать английский язык.
- Использовать только строчные буквы.
- Разделять слова дефисом (`-`).
- В начале указывать тип задачи.
- Название должно кратко отражать суть изменений.
- Не использовать пробелы и специальные символы.

Если задача имеет номер в GitHub Issues, рекомендуется добавлять его в название ветки.

Пример:

`feature/15-equipment-search`

## 4. Жизненный цикл веток

Рабочие ветки создаются непосредственно перед началом выполнения задачи.

Порядок работы:

1. Создать Issue или выбрать существующую задачу.
2. Обновить локальную ветку `main`.
3. Создать рабочую ветку от актуальной `main`.
4. Выполнить необходимые изменения и добавить коммиты.
5. При необходимости синхронизировать рабочую ветку с актуальной `main`.
6. Создать Pull Request.
7. Дождаться прохождения CI и получения одобрения от другого участника команды.
8. Выполнить слияние через Squash and merge.
9. Удалить рабочую ветку после успешного слияния.

Ветки должны существовать только в течение времени, необходимого для выполнения конкретной задачи. Не рекомендуется
использовать одну ветку для нескольких независимых задач или длительное время хранить завершённые ветки.

## 5. Правила слияния

Для слияния изменений используется механизм **Squash and merge**.

Он объединяет все коммиты рабочей ветки в один коммит при добавлении изменений в `main`.

Перед слиянием Pull Request должны выполняться следующие условия:

- Все проверки CI завершились успешно.
- Получен минимум один Approve от другого участника команды.
- Все замечания, блокирующие слияние, устранены.
- Конфликты слияния отсутствуют.
- Изменения соответствуют критериям приёмки задачи.

Прямые коммиты и слияния в `main` запрещены.

## 6. Требования к Pull Request

Каждое изменение должно сопровождаться Pull Request.

Требования:
- Название Pull Request должно полностью совпадать с названием связанной задачи в GitHub Issues.
- Каждый Pull Request должен ссылаться на соответствующую задачу.
- Для автоматического закрытия задачи после слияния используется ключевое слово `Closes #<номер задачи>`.
- Описание PR должно содержать краткое описание изменений.
- Должны быть указаны шаги для проверки изменений.
- Должен быть заполнен чек-лист автора.

Пример:

Issue: `#15 Добавить поиск оборудования`

Название Pull Request: `#15 Добавить поиск оборудования`

Описание PR:

Closes #15

## 7. Итоговые правила

1. Основная ветка проекта — `main`.
2. Разработка ведётся исключительно в отдельных рабочих ветках.
3. Для каждой независимой задачи создаётся отдельная ветка.
4. Названия веток должны соответствовать установленным правилам.
5. Все изменения проходят через Pull Request.
6. Для слияния требуется минимум один Approve.
7. CI должен завершиться успешно.
8. Слияние выполняется через Squash and merge.
9. После слияния рабочая ветка удаляется.
10. Прямые коммиты в `main` запрещены.
